# AI/ML Technical Requirements — Implementation Matrix

Client-facing summary mapping each requirement to how it's implemented —
named components (Feast, MLflow, DBSCAN, regex/static rules, etc.), not
generic "AI-powered" language. Based on `docs/ai_ml_technical_compliance.md`;
add rows as further requirement text comes in.

| Technical Requirement | Implementation Summary |
|---|---|
| Defense-in-depth architecture — ≥3 independent, sequential, complementary filter layers | • Deterministic **Rule Engine** (blacklist/whitelist + regex pattern matching) screens every message first, resolves obvious cases immediately.<br>• Unresolved traffic moves to a **behavioral/graph layer** (sender velocity, fan-out, communication structure).<br>• Then **parallel ML scoring** — a trained pattern model + an unsupervised anomaly model.<br>• A campaign must evade all layers, not just one. |
| Sender Blacklist/Whitelist filter — MSISDN, IMSI, Sender ID, range, prefix | • Deterministic lookup in the Rule Engine — match/range/prefix check against configured entries, before ML scoring.<br>• Whitelisted traffic skips scoring entirely.<br>• Every outcome logged as a labeled example, keeping the ML layer aligned with the Rule Engine over time. |
| Pattern/Keyword filter — exact, substring, regex, near-match (O→0, 1→!, Unicode homograph) | • Exact/substring/regex matching — existing Rule Engine's job, already handled there, no change needed.<br>• Near-match/homograph normalization — **not** done by the Rule Engine today; this is an **AI/ML-owned build**.<br>• Runs as a text-normalization step *before* the Rule Engine's pattern check and before embedding/fingerprinting.<br>• Rewrites evasive variants (O→0, look-alike Cyrillic/Greek letters) to canonical form before either stage sees them. |
| Dynamic Filters — Volumetric Filter | • **Features per sender:** message count (1 min / 5 min / 1 hr); distinct destinations (5 min / 1 hr); recipient-diversity ratio (distinct destinations ÷ message count); repeat-content ratio (1 hr); velocity z-score vs. sender's own running mean/stdev; sender age in days.<br>• IMSI-linked senders (SS7) also get distinct-originators-per-IMSI in the trailing 1 hr — the SIM-Farm signal.<br>• **Process:** each feature computed using only messages strictly before the current one (point-in-time correct, no lookahead) — training and live scoring see identical logic.<br>• z-score baseline is a running mean/stdev per sender (Welford's algorithm), not a fixed global threshold. |
| Dynamic Filters — Social Graph Filter | • **Features per (source, sender, recipient) pair, per configurable window:** outbound count (A→B), reciprocal count (B→A), one-way ratio between them.<br>• **Process:** pair messages by matching sender/recipient in each direction within the window, reusing the same point-in-time windowing as the Volumetric features.<br>• One-way alert fires when outbound count exceeds a configurable threshold while reciprocal count stays near zero.<br>• **Prerequisite:** needs both directions of traffic ingested. Directly buildable where both legs are already captured; where only outbound traffic is ingested, enabling two-way tracking is a data-capture scope decision, not just a new feature — called out explicitly. |
| Machine Learning Filters — Fingerprint / Originator / Mobile Number Reputation, in parallel | • Two models score every message in parallel: a **supervised model** on confirmed Rule Engine outcomes, and an **unsupervised anomaly model** on content embeddings, fingerprint matches, and behavioral history.<br>• Output feeds three reputation signals — content fingerprint, sender history, numbers referenced in message text.<br>• Training/versioning tracked in **MLflow**; features served consistently at train and score time via **Feast**. |
| Real-time AI/ML detection and classification, in production | • Live scoring calls the same trained models validated offline — no separate re-implemented fast path.<br>• **Feast** serves the same point-in-time features at scoring time as at training time, so live decisions match what was tested. |
| Automatic campaign clustering — no manual per-template config | • New campaigns found via **DBSCAN** clustering over anomaly-flagged messages — no template registration needed.<br>• Clustering runs on content similarity (embedding + fingerprint); sender behavior applied after, as enrichment, not part of the clustering distance itself.<br>• Keeps one campaign from splitting across clusters due to sender differences. |
| Learning/policy update from analyst (Fraud Analyst) feedback | • Discovered clusters go to an analyst for review.<br>• Only analyst-confirmed clusters become training data.<br>• Unconfirmed system suggestions sit in a separate track and can never auto-promote to production. |
| Dedicated algorithms per threat type — not one general model | • **SIM Box/Farm** — IMSI-linkage cardinality check (rule, not ML).<br>• **Grey Route/A2P Bypass** — Volumetric filter.<br>• **App Farm** — behavioral velocity.<br>• **Phishing** — trained content/anomaly model.<br>• **Malware** — link/URL reputation, currently the one gap, called out directly as a delivery item. |
| GenAI/LLM-enhanced detection and response | • Content embedded via a multilingual sentence-embedding model, capturing meaning, not exact wording.<br>• This already lets reworded GenAI variants of a known campaign match as the same campaign.<br>• Explicitly flagging "this text was LLM-generated" is a further capability planned on top of this embedding base. |
| Continuous recording/monitoring of analyst decisions on Suspect cases | • Every analyst confirmation logged, kept distinct from unconfirmed system suggestions.<br>• Only confirmed decisions retrain the model.<br>• Auditable trail from system suggestion → human confirmation → retrain. |
| Configurable Decision Type, Risk Score Threshold, automation level | • Two risk scores (pattern, anomaly) kept separate, not blended, so each thresholds independently.<br>• Model parameters versioned and logged per run in **MLflow**; rule-vs-ML routing already configurable.<br>• One unified admin panel tying these into Decision Type / Threshold / automation level is the remaining integration step. |
| Social Graph — two-way (A→B, B→A) history per pair, configurable window | • Built by pairing messages each direction within a configurable window per sender/recipient pair.<br>• Fully buildable on channels that already capture both directions.<br>• On channels capturing only outbound traffic, two-way tracking needs a data-capture scope change (bringing in the reply leg), not just a modeling change — flagged explicitly. |
| One-way communication detection and alerting | • Built on the pair-tracking above: outbound vs. reciprocal volume compared per pair per window.<br>• Alert fires when outbound crosses threshold with near-zero reciprocal traffic.<br>• Same rolling-window approach as existing per-sender volume monitoring, applied at the pair level. |
| SIM Farm identification + auto policy propagation to the group | • Sender identity (claimed number/ID) tracked separately from physical identity (IMSI); many claimed identities on one IMSI is a direct SIM Farm signal.<br>• Clustering already groups senders sharing content.<br>• Auto-propagating "one member confirmed spam" to the whole group is a direct extension of the existing confirm/retrain pipeline — wiring it to fire automatically is the remaining step. |
| Grey route detection — same content across multiple routes/connections | • Existing content-fingerprint matching extended to compare the route/connection each occurrence came in on.<br>• Same content, unexpected route → flags as grey-route.<br>• Reuses fingerprint infra, no new detection mechanism needed. |
| Fully automatic real-time clustering, no manual config | • Matching a message against an *already-fingerprinted* campaign is real-time, per message.<br>• Discovering a *brand-new* campaign shape currently runs as a scheduled job, not continuously on the live stream — called out directly rather than assumed solved. |
| Reputation scoring mechanism (shared by all three reputation types below) | • Score range: 0.0 (bad) to 1.0 (clean), starts neutral at 0.5.<br>• **Update:** on each confirmed outcome, exponentially-weighted moving average — `score = (1-α)×score_old + α×outcome`; analyst confirmations get higher weight (α) than automated rule outcomes; unconfirmed ML flags never update it, avoiding a self-reinforcing feedback loop.<br>• **Recovery:** on a schedule, an inactive score decays back toward 0.5 — `score(t) = 0.5 + (score_last − 0.5) × e^(−t/τ)`, τ = configurable recovery time-constant. Repeated bad events keep it low; going quiet lets it heal.<br>• **Storage:** per entity (fingerprint/sender/number) in the feature store.<br>• **Consumption:** feeds both the ML models and direct Rule Engine cutoffs (e.g. score < 0.2 → auto-BLOCK). |
| Content/Fingerprint Reputation — normalization, fingerprint, score updated from Campaign Classification | • Content normalized and fingerprinted; real-time matching (1h/24h windows) already tracks match count, distinct senders, similarity.<br>• Entity key = fingerprint.<br>• Applying the scoring mechanism above to turn these match stats into a persistent score is the near-term step. |
| Originator Reputation — dynamic score, activity-driven, with recovery mechanism | • Sender activity (rate, diversity, repeat-content, age) already tracked continuously.<br>• Entity key = sender.<br>• The scoring mechanism's recovery/decay half is the piece that doesn't exist today; everything else is a direct extension of existing tracking. |
| Mobile Number Reputation — extract numbers from content, score them | • The one dimension with no groundwork yet — no number extraction exists.<br>• **Build:** extract from normalized text, standardize format, apply the same scoring mechanism with entity key = number.<br>• Catches scam campaigns reusing one callback number across many senders/wordings. |
| Embedding Vector — word-level + contextual semantics | • Every message becomes a dense vector via a multilingual sentence-embedding model — meaning-based, not word-by-word, so context shifts the vector.<br>• Dimensionality-reduced for fast real-time comparison at scale. |
| Semantic Morphing — detect similar-meaning messages despite different wording | • Direct use of the embeddings above: differently-worded, same-meaning messages land close together in vector space.<br>• Similarity search + fingerprinting clusters them as one campaign with zero exact-phrase overlap.<br>• Same mechanism as near-dup detection, applied to paraphrased variants. |
| Auto-apply confirmed Spam label to new campaigns with high semantic similarity | • Confirming one cluster member already propagates to the rest of that cluster.<br>• Extending this to *any* new campaign landing near it in embedding space, above a configurable similarity threshold, is the next step on the same similarity-search infra — not a new mechanism. |
| Auto-classify new campaigns (Spam/Scam/Phishing/Legitimate) by semantic similarity | • A supervised classifier trained on confirmed labels is the mechanism — trained on embedding features, so it effectively classifies by similarity to confirmed examples.<br>• The label pipeline is live; training/deploying the classifier is gated on enough confirmed volume per category. |
| Detect GenAI/LLM-created or -transformed campaign content | • The embedding approach already catches this indirectly (groups by meaning, regardless of wording).<br>• An explicit "this text looks LLM-generated" detector, independent of similarity to a known campaign, is a separate add-on still to build. |
| ML model management — update/replace models, configure parameters, monitor status, zero service disruption | • Every model version registered in **MLflow** with full parameters/metrics/lineage logged automatically.<br>• Promotion = reassigning a "champion" pointer in the registry; the live service always loads whichever model holds that pointer, per data source — swap without redeploying.<br>• Registry state also gives live visibility into what's deployed and how it's performing. |
| Setup-parameter reference and userguide — semantic weight calibration, AI model parameters | • All model settings (regularization, tree depth, embedding dimensions, clustering/similarity thresholds) are named, explicit config, not hardcoded.<br>• Every run's exact settings auto-logged to **MLflow**.<br>• A consolidated setup guide, including embedding/similarity calibration weights, can be compiled directly from this logged configuration. |
